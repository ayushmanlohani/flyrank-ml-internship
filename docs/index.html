FlyRank ML Internship · Lane 2: Refresh / Content Opportunity Scoring · Capstone
Abstract. Content teams must decide which pages to refresh first with limited editorial time — can trailing content signals rank that queue? We use the public-safe bundled slice (data/raw/content_refresh_anonymized.csv, 30,000 pseudonymized pages, 32 clients, base decline rate 54.2%). We compare a transparent hand-rule baseline against a Random Forest (100 trees, depth 10) on the same client-grouped holdout (25 train / 7 test clients, seed 42, leakage columns excluded). The model shows directional skill on the honest split (grouped ROC-AUC 0.610 vs baseline 0.500) but loses to the baseline at the very top of the queue (Precision@50 0.56 vs 0.70), while a naive random split overstates skill (0.77). We ship the result as a human-reviewed refresh queue with reason codes, not an autonomous publisher.

1. Introduction / Problem statement

Research question: Can we predict near-term organic traffic decline from trailing content metrics to prioritize manual content refreshes?

Decision supported: which pages a content editor reviews first each month. Unit: one pseudonymized page. Output: a ranked refresh score + reason codes. Human action: review top-K, check intent/seasonality/brand risk, then refresh, monitor, or skip. Cost of error: false positives waste editor time on healthy pages; false negatives let declining pages keep sliding. ML helps because decline is multi-signal (visibility × age × position × engagement) — no single threshold captures it.

2. Data

Release used for modeling: bundled anonymized starter slice data/raw/content_refresh_anonymized.csv (30,000 rows × 44 columns). This is the public-safe slice that ships in the repo — no client names, domains, URLs, titles, or queries, only hashed content_id/client_id plus numeric/categorical metrics.

Relation to warehouse: the full internship warehouse (~79M daily rows, ~70 clients, Feb–Mar 2026 windows) is the lane context from notebook 03; all capstone modeling numbers below come from the starter slice so anyone can reproduce without gated access.

Label window logic on slice: is_declining_label = (trend_direction == "down"); base rate 54.2% (16,262 / 30,000). No rows dropped.

Excluded — and why: trend_direction, trend_pct (label-derived, would leak); content_id, client_id (pseudos — grouping only, never features, per DATA_USE.md); product flags absent by design. Rate columns are 0–100 scale (0.76 = 0.76%).

3. Methodology

Assumptions: past 90-day visibility/engagement + age/freshness carry directional signal about near-term decline; clients are distinct domains so generalization must be tested across clients, not rows; refresh need is a ranking problem, not a hard classification.

Features (27, fixed): numeric — search_volume, competition, cpc, word_count, char_count, log_impressions_90d, log_clicks_90d, log_sessions_90d, log_ai_sessions_90d, days_with_impressions, days_with_sessions, content_age_days, days_since_last_update, ctr, avg_position, engagement_rate, scroll_rate, ai_traffic_pct; categorical — competition_level, content_type, main_intent, age_tier, freshness_tier, word_count_tier, impression_tier, position_tier (label-encoded). Left out on purpose: label-derived + IDs (above).

Label: is_declining_label in one sentence — page's trend bucket is "down".

Baseline (fair comparison): transparent hand rule (days_since_last_update >= 180) * impressions_90d — "stale and visible first". Same test rows, same metrics as model.

Validation: primary = GroupShuffleSplit on client_id, 20% clients held out (25 train / 7 test, seed 42); contrast = stratified random split to demonstrate over-optimism. Leakage checks: assert no trend_* in features; assert no shared client_id across train/test; assert IDs never encoded as features.

Error pattern (observed): largest misses are low-volume pages (1–2 impressions) where one click = 100% swing, often fresh pages (~20 days) not yet stabilized — the model under-scores true declines there and over-scores stable high-visibility pages with thin engagement. Implication: gate low-impression rows to monitor, not refresh.

5. Limitations & honest framing

  • Observed only, not causal: directional, decision-support signal. No claim about Google's algorithm or that refresh causes recovery.
  • Survivorship: needs history; brand-new pages (first ~30–60 days) cannot be scored reliably.
  • Intent blindness: high-level intent buckets only; a page can decline because intent shifted, which no refresh fixes — human intent check required.
  • Seasonality / calendar: trend buckets are window-sensitive; verify against prior period before acting.
  • Slice-bound: numbers measured on the 30k starter slice; warehouse-scale behavior may differ. No private queries or client-identifying detail published.

Reason-code glossary: STALE_CONTENT (>180d since update) · STRIKING_DISTANCE (pos 4–10 + demand) · LOW_CTR_HIGH_VIS (high impressions, low CTR) · LOW_ENGAGEMENT · MODEL_DECLINE_RISK (RF prob high).

Protocol: review top 50 monthly; never auto-publish brand/legal pages; log decision (refreshed / monitored / skipped + why) so next cycle learns. Confidence: directional — expect ~56–58% hits in top-50/200 on similar slices, not guarantees.
